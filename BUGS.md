| 2026-09-19 | Closing the app window with the X left the server running, and double-clicking the launcher then did **nothing at all** — no window, no error | the launcher ran `cmd /c node scripts/dev.js --built > .server.log`, and `>` takes an **exclusive** handle on the log. The instance left behind by the X still held it, so the new `cmd` failed on the redirect *before node ran*. Measured: a second redirect to the same file gives "The process cannot access the file because it is being used by another process", and `openSync('.server.log','a')` against a live old-style instance is `EBUSY` | the `.bat` calls `scripts\launch.ps1`, which starts node hidden with **no redirect**; `dev.js` writes the log itself, with synchronous writes (a stream's buffer is lost to `process.exit`). And the server surviving the X is now used rather than fought: if one is already answering on 5174, `dev.js` just opens another window onto it and exits — **the Claude session inside it keeps running** — while `--force` (or `stop-gcode-studio.bat`) still gives a clean restart. Confirmed by the user: window back, chat still there |
| 2026-09-19 | **B17** — the print check reported **4 HIGH "thin screw seat"** on a phone case, which has no screws at all: its hexagon cut-outs were being read as screw holes with a head pocket (shaft r 5.2–5.3, "pocket" r 5.86–5.94 up to Z 0.28–0.48) | two independent false positives, both general, not about this part. (1) The roundness test read the radius **only at the ends of the moves** — and every end point of a straight-edged hole is a corner, all at the same radius, so a hexagon scored rMax/rMin **1.008**, rounder than a real sliced circle. Any polygonal hole ≤ 6 mm passed. (2) A "head pocket" only had to be 0.6 mm wider in radius than the shaft, which the first layer's elephant-foot widening (and a chamfer at the mouth of a hole) reaches on its own — here 5.94 vs 5.28, a factor of **1.12**, while the measured real pocket is 3.15 vs 1.75, a factor of **1.80** | `loopShape()` samples the radius **along** the path every 0.3 mm (bounded to 256 samples, behind a cheap bounding-box reject, so the cost is unchanged: 23–43 ms on 92,664 moves): a hexagon now reads **1.155** and a polygonised circle 1.01–1.08, and `maxRound` 1.10 splits them. A pocket must also be **≥ 1.25 ×** the shaft radius (`pocketRatio`). Both demo files: 4 HIGH → **0 HIGH**, nothing else in the report moved. The real screw-seat files are on the archive machine, so `check-printcheck.js` gained four synthetic cases that run anywhere — the measured hole (pocket r 3.15 to Z 2.4, shaft r 1.75) flagged at a 1.2 mm seat and clean at 2.2 mm, a hexagon cut-out not a screw hole, and first-layer widening not a pocket |
| 2026-09-19 | `test/server-slice.js` said a fresh slice was not byte-identical to the committed reference — i.e. the claim the whole re-slice lane rests on looked false | not the slicer, the profiles or any post-processing: **git**. `core.autocrlf=true` with no `.gitattributes` checks the demo G-code out as CRLF (3,088,226 bytes) while the commit holds LF (2,963,504). The slicer writes LF, so the comparison was really asserting on the reader's git config. `git show HEAD:<file>` gave a file the same size as the fresh slice, differing on **one line**: the `; generated by … on <date>` stamp. Two consecutive slices differed only in that stamp too | `.gitattributes` with `*.gcode -text` (also `*.stl`, `*.3mf`), and the two demo files rewritten to the bytes that were committed. The test now (a) slices twice and compares the two outputs directly, which needs no repository at all, (b) compares against the committed file line-for-line with line endings normalised, printing the first differing lines when it fails, and (c) checks all 624 CONFIG_BLOCK keys match, so "the profiles in the job folder are the ones that produced this file" is asserted on its own. 24 → 30 checks, 0 failed |
| 2026-09-19 | **B15** — a file from another printer or slicer could be opened, measured, diffed and checked, but not written to at all | the safety gate required *this* machine's five end markers (`;PRINT_END`, `M104 S0`, `M140 S0`, `M84`, `; EXECUTABLE_BLOCK_END`) as a hard error; `;PRINT_END` comes from this `machine.json` | an edit is now held against the end sequence **the source file actually had** — every shutdown marker in the original's tail must survive the edit.
